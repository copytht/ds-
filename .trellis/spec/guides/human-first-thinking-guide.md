# 人先思考（human-first）

**规矩：如果人很容易做到，优先用人的方式。** 2026-10-04 用户拍板。

做判断 / 操作页面之前先问一句：「**人在这儿是怎么做的**？」——人看什么信号、按什么顺序、
怎么确认自己做对了。人用的信号通常落在**渲染结果**里（样子、位置、颜色、顺序），
而不是实现细节里（class 名、内部状态、接口形状）。实现细节是站点/框架的私事，说改就改；
渲染结果是**给人看的**，站点自己最不敢乱动。

## 正例：判断一条消息是谁说的

- **人**：看**气泡**。用户的消息被画成一个圆角块、贴右、有底色；助手的是整宽素文。
  （真机量过：用户 `border-radius: 22px` + 底色 `rgb(237, 243, 254)` + 右缘贴行右缘。）
- **我们最初的做法**：认站点的设计系统类 `.ds-assistant-message-main-content` /
  `.ds-collapsible-text`——站点换版把这批类撤了，判据就断。
- **改用人的方式**：认「这行画没画气泡」（`getComputedStyle` / `getBoundingClientRect`），
  与 class 无关。代价是要研究「气泡 vs 助手内容里的代码块底色」怎么分。

## 边界：什么时候**不**用人的方式

人的方式也有慢 / 有损的时候（长对话要滚屏拼接、文字从像素读回来会错、这条链的 agent 收不了图）。
那时才退回机器方式（流式载荷 / 站点接口 / DOM 结构），并且在 design 里写清**为什么**。

## 落到代码

「人的信号」常常要读**渲染**（几何 / 样式）。jsdom 不做布局——`getBoundingClientRect` 全零、
`getComputedStyle` 没有真底色。所以这类判据要留一个**探测口**（把 `getComputedStyle` /
`getBoundingClientRect` 包成可注入的替身），真机走真 DOM、单测喂假数据；否则测试是**假的**。
