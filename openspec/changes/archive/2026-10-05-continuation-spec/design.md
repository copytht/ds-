# Design

## Context

ADR-0014 定了一件重要的事：**工具结果的正文不再作为可见用户消息进对话，改走出站请求体替换**，
可见面只留两行短标记（风控动机：账号被阶梯处罚 3 天→8 天，可见消息条数是唯一能自己压住的
行为面）。配套是 8 轮刹车、2000 字截断、武装时机在放行那一刻。

这套口径**只存在于 ADR 正文与代码注释**。`openspec/` 五篇 spec 下 grep `continuation` /
`续聊` / `短标记` / `rounds` **0 命中**。ADR 改了口径不会让任何一扇门变红——于是：

- #47：ADR-0014 说「`wait.reply` 口径变小」（`:43`），但 `local-tools` 的 spec、fixture、单测
  三处都还假设旧的长 TOON 形状，于是 `send.page` 每次 `page-changed`；
- #48：「唯一出站口」写在 CONTEXT 词条与 ADR-0002 里，但**没有 requirement 管「哪些发送路径
  受哪些闸」**，于是第二条路悄悄长出来了；
- #49：「宁可少一轮也不能吃人说的话」是注释，30s TTL 与 3–5s 窗口的比例没人算过；
- #51：「失败只进控制台」是 `local-tools` 对模型调用的口径，续聊自己那份没有 requirement。

## Goals / Non-Goals

**Goals:**

- 把 ADR-0014 / ADR-0002 的既有决定落成**可校验**的 requirement。
- 让 #47–#51 各自的「该改成什么样」从 requirement 里直接读出来。

**Non-Goals:**

- **不改代码**。代码偏差由 #47–#52 各自去修；本 change 只补规格。
- **不替 `send.page` 定新口径**（撤掉 / 拆两个 / 等正文要人拍板，#47）。spec 里标为待定 +
  现状注记，不先填一个数。
- 不改 ADR 本身——它是对的，本 change 是让它可校验。

## Decisions

1. **新能力叫 `continuation`**（不复用 `local-tools`）。它不是「本地工具」：它没有模型调用方、
   由扩展自己发起，主体是「出站窗口 + 武装 + 刹车 + 请求体替换」，跨越 MAIN 世界与
   `src/lib/inject.ts` / `gate.ts` / `rounds.ts` / `continuation.ts` 四个模块。塞进
   `local-tools` 会让那个能力的「失败只进控制台」口径继续罩着它（#51 的成因正是这个）。

2. **「出站窗口是唯一收口」这条 requirement 特意写窄**——只约束**自动续聊**这一路，并明写
   「手动页面动作与看门狗催办不受它约束」。这不是修文档的借口（#48 的文档半张另行处理），
   而是 spec 必须说清真实边界：把假的「唯一」写进 requirement，下一个人会照着它推理。

3. **`local-tools` 那条用「现状注记」而不是直接改口径。** 拍板前把「三方证据与真实链路不符」
   写在 requirement 里，是为了让下一个读 spec 的人**看见这件事**，而不是以为 spec 描述的是
   正确行为。注记里列出三条修法与「本 spec 不先填新口径」，避免 agent 擅自挑一条实现。

4. **不为「武装 TTL 30s」写 requirement。** #49 要修的就是它；现在把 30 秒写成 requirement 等于
   把一个待修的数钉成契约。`continuation` 的武装那条只写**时机**与**一次即作废**（ADR-0014 的
   既有决定），不写 TTL 数值——TTL 是待修项（#49），归零/作废的语义写「过期限就作废」而不给数。

5. **失败处置与留痕分成两条 requirement。** 「失败一律作废这一轮、不重试、不留半截」是行为，
   「结果没送到模型手上 ≠ 中继没连上」是**可观测性**（ADR-0010 的延伸）。混成一条会让 #51
   的粒度问题（只进控制台 vs 要不要翻图标）无处安放——那是它需要人拍板的地方。

## Risks / Trade-offs

- [补了 spec 但代码仍不合规] 本 change 不修代码，所以 `pnpm quality` 里 `#47` 那条失败**仍然
  存在**。这是有意的：spec 先落地会指出该怎么修，但**别让「spec 齐了」被当成「问题解决了」**。
  #47 仍要单独修（且要人拍板）。
- [新能力与 ADR 双份叙述] ADR 讲「为什么这么定」，spec 讲「必须怎样」，两者会重复。取舍：
  spec 只写可校验的**约束**，理由留给 ADR；将来改口径时以 spec 为门、ADR 为历史。
- [8 轮 / 2000 字 / 3–5 秒这三个数被写进 requirement] 它们是「写死」的决定（ADR-0014 的
  Considered Options 明说轮数先写死、要调再加 storage 覆写）。写进 spec 意味着**改动需要走
  spec 变更**——这是有意的，它们正是风控参数，不该随手改。
