# Design

## Context

`send.page` 是 ADR-0013 落的 v1：issue #23 要「往页面发一个问题 → 等页面模型排围栏 →
等回灌 → 取答复」，ADR-0013 论证 dsb 侧指挥不动扩展（ADR-0011 废掉了反向通道），于是把
组合搬到扩展侧的本地工具名册。

ADR-0014（2026-10-04，本仓）把工具结果从「可见的长 TOON 消息」改成「出站请求体替换 + 两行
短标记」，`send.page` 没跟着改，于是链条的三段各自失联：

| 那一段                             | ADR-0014 之后它在等什么                                                                                            |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `composer.type` + `send.enter`     | **仍然成立**（发一条真问题进页面）                                                                                 |
| `wait.fence`                       | 等页面模型排的围栏——而那条围栏被 `detect()`（`inject.content.ts:206`）捕获后走 `sendCalls`，与本地工具这条路无关   |
| `wait.reply` + `parseReplyPayload` | 等首行锚 `agent:` 的回灌——**那正是它自己触发的那一轮**（自指），而正文已不进可见消息，TOON 解不开 → `page-changed` |

## Goals / Non-Goals

**Goals:**

- `send.page` 不再必然失败（#47），并消除「同一份工具结果被回灌两次」。
- 协议说明对模型的承诺与实现一致（`instructions.ts:50` 那个假承诺）。

**Non-Goals:**

- **不撤掉 `send.page`**（理由见下）。
- **不解决 issue #23 的原始需求**（「组合工具任何 agent 开箱即用」）——那要重开双向通道，
  ADR-0013 已记为「另一件事，另开任务」。
- 不动 `wait.reply` / `wait.fence` 这两个页面动作本身（它们仍在 `ACTION_ROSTER` 里，
  只是 `send.page` 不再用）。`parseReplyPayload` 也留着（别处还在用）。

## Decisions

1. **缩成两步，删掉「取答复」这半边。** `send.page` 变成「往页面发一条问题」这一件。
   理由：模型**读不到页面消息**——页面动作没有 MCP 工具面（`dsb/` 下 0 处动作名；
   `background.ts:619-639` 的工具目录只取 dsb 的 `tools/list` + 过滤 `said_*`）。既然
   工具没法替模型读回答，「等回灌 + 取答复」就是一段**做不到**的承诺，而不是一个待修的 bug。

2. **返回空的确认，而不是回答正文。** 两步走完即回确认。模型从**下一次输入**里看到页面的
   新回答——那条回答会经 `detect()` 被看见、若排了围栏就走 `sendCalls` 正常工具路径。
   也就是说这个循环**本来就是闭的**，不需要工具在自己内部再等一遍。

3. **保留 `send.page`，不撤。** 它是 ADR-0013 的落空产物（issue #23 要的是「agent 开箱即
   用」，而扩展侧本地工具只有围栏里的**页面模型**能排——ADR-0013:23-24 自己承认「外部 MCP
   agent 依旧调不到页面动作」），所以它在原意上该撤。但撤的收益不足：
   - `local-tools` 9 条 requirement 里大半要动，`instructions.test.ts` 的对拍对象没了；
   - **issue #23 的真需求仍然没满足**——撤掉不解决它；
     而「让页面模型给页面发一条新消息」这个窄能力**无害**，前提是不再撒谎。

4. **把落空这件事记进 ADR-0013 的补记。** 用户点过这件事：issue #23 的原始需求仍未满足，
   要靠重开双向通道（ADR-0013:31 原文已经这么留了口）。补记把它和本次的取舍钉在一起，
   免得下一任以为 `send.page` 就是 issue #23 的答案。

5. **失败处置口径补上 `page-changed`。** `instructions.ts:51` 原来只写「闸挡下 / 超时 /
   页面不在…当作没排过，别重排」。模型收到别的码（例如两步走完但页面形状不对）时
   无从判断该不该重排——**这是行为未定义**，不是「必然重试」。本 change 把该口径写全。

## Risks / Trade-offs

- [模型对「发完就收到确认」不适应] 协议说明里写了它会看到页面的新回答；真机复验要确认模型
  **不会**因为确认来得太快而重排同一块围栏。回灌与确认的时序在真机上走一遍才知道。
- [两步之后 `seconds` 参数无意义] 收缩成「发一条问题」后 `seconds`（等多久）没有对象了。
  取舍：**删参数**（`question` 单一入参）——留着会让模型以为要等。`normalizeSeconds`
  与它对 `wait.*` 的钳位如果别处还在用就留着，单测同步。
- [与 #48 的重叠] `send.page` 是 #48 里「不经 `gate.ts`」的两条路之一。本 change 只修它自身
  的失败，**不解决**它绕过出站窗口的问题（那要跨世界重构收口，另议）。
- [双重回灌消失的副作用] 以前模型会收到两份回灌（围栏那次 + `send.page` 返回那次），
  现在只剩一份。若有谁依赖过那份重复，行为会变——单测里有一条正是靠它拿回灌文本的，
  改测试时要确认改的是「测试的口径」而不是「掩盖了重复」。
