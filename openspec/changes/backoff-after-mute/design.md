# Design: 出站退避

## Context

见 proposal.md - Why。约束：

- 判据只能来自站点自己给的东西：警示条里的处罚句与解封时刻（纯文本，`page.ts` 已能读）。**不猜**：限流信号、时长、并发数，站点都不给。
- 退避是出站口之外的一层闸。出站口（ADR-0002：唯一出站口、3~5s 窗口）原样保留——退避从不自己发消息。
- 存储面与总开关、「替人开口」同一处（`browser.storage.local`）。

## Goals / Non-Goals

**Goals**

- 认出禁言（`muted`，带不带时刻都算）后，写动作不再推到页面，当场回结果。
- 三态迁移只认站点给的信息；退避时长按阶梯增长并持久化。
- 长休到点后，第一笔写动作先探活再放行。

**Non-Goals**

- 不改变出站口本身、不新增发送路径。
- 不做「猜站点限流算法」——站点不给的信息一律不猜，退避时长只按阶梯取，不按站点行为拟合。
- 不动中继。

## Decision

**三态与迁移**：

```
正常 ──(page.state 认出处罚句)──→ 长休(until)
长休 ──(到了 until，第一笔写动作探活成功)──→ 正常
正常/长休 ──(收到限流类信号)──→ 退避(t = 阶梯)
退避 ──(t 到了，探活成功)──→ 正常
```

- 「限流类信号」在本仓库里**目前没有**——动作失败码册子里没有 rate-limit 码。所以退避态的第一版**只从长休迁移进来**，不从「收到限流信号」迁移。阶梯增长先写好，但触发点留空（Open Question 1）。
- 长休的 `until` 是页面上的纯文本正则抠出来的；**到点不自动恢复**，第一笔写动作先做一次只读探活（写作框在不在），在才恢复。这是有意的保守：`until` 的出处是站点文案，站点改措辞我们就得跟着改。

**失败码**：退避中、长休中的写动作回 `disabled` 还是新码？**回 `disabled` 不行**——`disabled` 的语义是「总开关关着」（用户可自己翻回来），而退避是扩展自己的判断，用户翻总开关救不了。新码 `backing-off` 进册（三处同步：`protocol/fixtures/action.json`、`dsb/actions.py`、`tests/test_actions.py`，这是 ADR-0010 定下的规矩）。

**退避时长**：阶梯取——第一回 10 分钟，之后每回 ×2，封顶 8 小时。写进持久存储（键 `backoffUntil`），重启后仍记得。**没有站点依据**，纯约定；design 的 Open Question 2 会问要不要做成配置。

## Risks / Trade-offs

- **误伤**：警示条判据若把公告当处罚（现有判据已防：须同时提到「账号/你」与「禁言/封禁」），退避会把活全拦下。护栏：只读动作永不受退避影响，`page.state` 永远可读，人能看见处境。
- **`until` 认不出**：处罚句在但时刻抠不出 → `until = null` → 长休**没有终点**。这时不能无限停：退避层对 `until = null` 的长休按「退避态」处理（阶梯有终点）。这是刻意的兜底。
- **站点改文案**：正则失效 → `unknown`（不猜）→ 不退避，照旧干活。已知风险，接受。

## Open Questions

1. **退避态的触发点**：现在动作失败码里没有 rate-limit 码，退避态第一版只从长休迁入。要不要给「站点返回限流」一个码并接进退避？（需要先抓到站点限流时的真实失败形态——禁言期间抓不到。）
2. **退避时长要不要可配**：10 分钟 ×2 封顶 8 小时是约定。做成 `options` 页一个输入框，还是写死？（写死更懒；可配更方便真机调。）
3. **探活的代价**：长休到点后的第一笔写动作会先触发一次只读判定。若站点在「解封时刻到了但写作框还没渲染」的窗口里，会多拦一笔。可接受？
