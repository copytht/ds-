# ADR-0028: DeepSeek 网页端单条消息的输入上限是按 token 计的（实测 ~98 万 token）

- **Status**: accepted
- **Date**: 2026-10-09
- **Supersedes**: none

本篇回答「网页输入上限是多少」——用 DeepSeek 自己的分词器数 token，
而不是用字数边界反推。结论是一个 **token 预算**，不是字数。

## 结论先摆

**网页端单条消息的输入上限 ≈ 98 万 token。**
收下/拒收的分界在 **982,000 < 上限 < 982,700 token**（用 `finish_reason`
硬判据二分，区间宽 700，约 0.07%——见下面「判据升级」）。

**但本仓对外按 900,000 token 记这个数**（`MAX_SAFE_INPUT_TOKENS`），
不取实测的 ~98.2 万。**理由是余量，不是测量精度**：

- 实测边界离 982,000 只差几百 token，而**服务端可以随时改**——它是
  按模型/账号下发的配置（ADR-0028 已记 `input_character_limit` 就是
  这么下发的），发版或灰度就能改。我们没有能力第一时间知道。
- **DeepSeek 已经有过「压缩机制」的先例**（上下文超限时会话侧截断/摘要，
  这类策略一旦上线，上限的语义会从「硬拒」变成「静默截断」）。那时按
  实测值贴边写，就是在赌它不变。
- 因此 `900,000 = 实测下限 − 一个数量级都不至于的余量`：留约 8 万 token
  （~8%）余量，让「服务端改小了一点」不至于立刻变成我们的失败。
- 这条是**工程决策**，不是测量结论——改 `MAX_SAFE_INPUT_TOKENS` 前先读
  这一段，别以为它是实测值。

换算成字数取决于文本密度（用 `deepseek-ai/DeepSeek-V3` 的
`tokenizer.json` 实测，词表 128,815）：

| 文本           | token/字  | 收下                          | 拒收                          |
| -------------- | --------- | ----------------------------- | ----------------------------- |
| 真实中文小说   | **0.628** | 1,555,554 字（977,438 token） | 1,565,655 字（983,785 token） |
| 重复单字「测」 | **1.000** | 982,000 字（982,000 token）   | 982,700 字（982,700 token）   |

**同一 token 预算，密度不同的文本能塞的字数差 ~1.6 倍**——所以
「上限按 token 计，不是按字符」成立。

**收敛是可验证的**：拿「测」×983,785 去打（**故意取非重复数的 token 数**）
→ 被拒；而 983,785 正是小说 155× 的 token 数。两种密度完全不同的文本在
**同一个 token 数**上分界，这不是巧合，是「按 token 计」的直接证据。

## 怎么测的：判据与一路上踩的坑

可靠的判据只有一条：**有没有真回复**（服务端收下才会生成回复）。
「达到对话长度上限」那句话**不能单独当判据**——它既在拒收时出现，
也在「回复完了、提示对话已满」时出现（2026-10-09 在 250 万字档
抓到过后者，差一点把结论写反）。

一路上踩了五个坑，都记下来，下次别再犯：

1. **全文搜「达到对话长度上限」会被上一轮残留渲染污染** → 发送前
   先确认那句话不在页上（预检），出现才计。
2. **素材自带 AI 免责声明**（小说是从 AI 输出里抓的，末尾带着
   「本回答由 AI 生成」）→ 把重复次数误计成回复数。素材要剥掉
   免责声明，让该串只可能来自真回复。
3. **大消息的回复流得慢**（155 万字的回复 45 秒时还在流）→ 免责
   声明要等回复完成才落。判「收下」要看**有没有素材里没有的新文字
   流出来**，不只是免责声明。
   3.5 **有更硬的判据，本篇当时没用上**（2026-10-09 事后逆向补上，见
   `dsweb/FINDINGS.md` §6.2）：拒收时服务端下发独立 error 帧
   `{"type":"error","finish_reason":"context_length_exceeded",
"clear_response":true}`。**该路径下 `v.response.status` 压根不下发**，
   所以本篇「搜页面文字」的做法虽然慢且易被残留污染，但结论仍成立——
   换成读 `finish_reason` 会又快又稳。
4. **「超长约 X%」不是 token 上限的读数**——它是另一个上限
   （前端的 `input_character_limit`，见下节），在它自己的
   量程（字符）上读数。拿它当 token 上限的判据会量错对象。
5. **`chat.new` 是 SPA 路由切换、不重载 `window`** → 页内钩子
   （`fetch`/`XMLHttpRequest` 补丁、素材）会跨会话残留；要整页
   `location.reload()` 才干净。且写作框在 `chat.new` 后要等一会儿
   才挂上，`sleep 2` 不够，会填进空页。

## 为什么是 token 预算：两种文本收敛

用分词器把边界消息逐条数成 token，两种密度完全不同的文本落在
**同一个** token 区间：

| token 数 | 真实小说         | 重复「测」 |
| -------- | ---------------- | ---------- |
| 977,438  | 收下（有真回复） | 没被拒     |
| 980,000  | —                | 没被拒     |
| 983,785  | 拒收             | 拒收       |

收下的最大 token 数与拒收的最小 token 数，对两种文本都落在
[980,000, 983,785] 里——**分界由 token 数决定，与字符数无关**。
这正是「按 token 计」的判据：若上限按字符，两种文本（0.628 vs
1.000 token/字）的分界字数会差 1.6 倍，不可能收敛到同一 token 数。

## 「超长约 X%」是什么：前端的字符上限（2.5 MiB），不是 token 上限

「超长约 X%」是**另一个**上限的告警，与本篇的 token 预算
无关——它量的是**字符**，不是 token：

- **上限 = `input_character_limit = 2,621,440` 字（2.5 MiB）**，
  服务端按模型下发的配置（`localStorage` 的
  `__ds_remote_feature_store_model` → `model_configs`），
  三个模型（快速 / 专家 / 识图）**全都是这个值**。
- **百分比 = (输入长度 − 2,621,440) / 输入长度 × 100**——
  即「你这条输入里，超过上限的部分占百分之几」。
- **只在输入超过 2,621,440 字、且提交 / 粘贴触发了拦截后才
  显示**（前端 `vB` 钩子：`i = limit !== undefined && len > limit`，
  百分比 `l = Math.round((len - limit) / len * 100)`；提交拦截
  `interceptSubmit` 与粘贴 `notifyPasteOverLimit` 才会把告警
  挂出来——所以只填不发时看不到）。
- 超过时前端**拦下发送**并弹 toast「内容超长约 X%，请删减后再试」。

用截图与几档实测全部精确吻合（1570 万字 → 83%、304 万 → 14%、
609 万 → 57%、914 万 → 71%、1218 万 → 78%）。

**所以网页其实有两道墙，量纲不同**：

| 墙                            | 上限                    | 量纲  | 超了的表现             |
| ----------------------------- | ----------------------- | ----- | ---------------------- |
| 服务端 token 预算（本篇主题） | ~98 万 token            | token | 回「达到对话长度上限」 |
| 前端 `input_character_limit`  | 2,621,440 字（2.5 MiB） | 字符  | 拦发送 + 「超长约 X%」 |

对真实中文小说（~0.628 token/字），服务端 98 万 token ≈
156 万字，**先于**前端 262 万字撞到——所以「超长约 X%」只在
远超 token 预算的巨量输入（> 262 万字）时才出现，是个**兜底
的 sanity cap**，不是有效约束。

**两道墙的长度对不上**：服务端 ~98 万 token
（中文小说 ≈ 156 万字），前端 2,621,440 字。对中文
（~0.628 token/字）前者先到；对英文（~0.25 token/字）
后者（262 万字）先到。

**为什么对不上——没摸清。** 先前那版写成「两个独立
的上限、互不相干、没有按 token 密度折算过」，那是
**描述现象，不是解释**：我不知道前端为什么取
`2,621,440`（= 2.5 × 2²⁰，像按「2.5 MB」拍的
整数），也不知道它和模型的 token 预算之间有没有
我还没找到的关系——比如它是否本为别的文本密度、
或别的用途（文件 / 附件？）而设。已确认的只有两件
事实：服务端按 token 在 ~98 万拒（复核见下），前端
按字符在 2,621,440 拦；两者**不随文本密度对齐到
同一个数**。关系待查。

**复核**（2026-10-09，整页重载后绝对干净的会话）：
小说 × 200 = 2,020,200 字 = **1,269,400 token** →
服务端拒收。它远超 98 万 token、却低于 2,621,440 字
按小说密度折算的 164 万 token——证明服务端上限就是
~98 万 token，而不是前端字符上限折算出来的那个数。

## 对仓库的意义

- **`read` 的单页 16,000 字（~1 万 token）远在 98 万 token 之下**，
  不构成约束——ADR-0027 已实测定案，本篇只是把「天花板在哪」补全。
- 它是**「续聊 / 大段发送」场景的天花板**：往网页塞超过 ~98 万
  token 的消息会被服务端拒（回「达到对话长度上限」）。
- 与 ADR-0027 记的「自家五件工具没有总量闸」缺口**无关**——那是
  内存/存储闸，这里是服务端的 token 预算，两回事。

## Considered Options

- **用字数当上限**（如「156 万字」）：密度一变就错（测字只能塞
  98 万字）。否决——上限本质是 token，字数只是它在某种文本下的投影。
- **用「超长约 X%」当 token 上限的判据**：它量的是前端的
  字符上限（2.5 MiB），不是 token 预算，量错对象。否决。
- **用「达到对话长度上限」当唯一判据**：它也出现在「回复完了提示
  对话已满」时，会把「收下」误判成「拒收」。否决——必须配合「有没有
  真回复」。
- **钉死到个位 token**：在 [980000, 983785] 里再二分，每次都要等
  155 万字的回复流完（分钟级），成本高。否决——±0.2% 的精度够用了。

## Consequences

- 网页输入上限有了 **token 口径**：~98 万 token（消息正文；总上下文
  还要加站点系统提示词，本篇没数）。
- 知道了密度换算：真实中文小说 ~0.628 token/字、重复单字 1 token/字
  （`deepseek-ai/DeepSeek-V3` 分词器）。
- **`MAX_SAFE_INPUT_TOKENS = 900_000`**（`src/lib/continuation.ts`）：
  实测 ~98.2 万，本仓按 90 万记，留 ~8% 余量应对服务端改值与上下文压缩。
  配一条测试钉住，别被「顺手改成实测值」带走。
- 探针手法沉淀：判「收下」靠真回复、判「拒收」靠上限字样 + 预检、
  素材剥免责声明、大消息要等回复流完。
- **「超长约 X%」已查明**：前端 `input_character_limit`
  （2,621,440 字 = 2.5 MiB）的超限百分比，与 token 预算
  是两道不同的墙（见上节）。

## 未验证项

- **两道墙为什么对不上——没摸清**：前端 `input_character_limit`
  （2,621,440 字）与服务端 token 预算（~98 万 token）不随
  文本密度对齐到同一个数。前端为什么取 `2,621,440`（=
  2.5 × 2²⁰，像按「2.5 MB」拍的）、它和 token 预算有没有
  我还没找到的关系（是否本为别的文本密度或别的用途而设），
  未知。能把两边关系解释清楚的才算摸清，现在只确认了
  「不随密度对齐」这一现象。
- **精确预算值**：已用 `finish_reason` 硬判据夹到 **982,000 < 上限 <
  982,700 token**（宽 700，约 0.07%）。再往里夹收益极小——**这个数是
  服务端下发的配置，会变**，所以本仓按 900,000 记（见「结论先摆」）。
  真要再精确，得先有办法感知服务端改值。
- **站点系统提示词占多少 token 没数**：它计入总上下文，所以消息预算
  = 总上限 − 系统提示词；总上限略高于 98 万。系统提示词不可见，没法
  直接量。
- **不同模型 / 模式是否共享这个预算没验**：深度思考、智能搜索开着时
  的预算是否相同，未测（本篇都在默认模式下测）。
- **「回复完了提示对话已满」那条路径的确切触发点没单独量**：它和拒收
  共用一句话，本篇靠「有没有真回复」把两者分开了，但前者的触发点
  （对话累计多少 token 后提示）没单独测。
