# 等待期观测走 opencode 的事件流，进度只从图标露出

中继把 `GET /api/event` 挂在 prompt **之前**，用「断流 / 停摆」当场判断等待该不该收场；
问句在途的现场（阶段、已写字数、剩余预算）经一个只读的 `GET /status` 交给扩展，只上角标与
悬停，**不进对话流**。正文判定仍以 `GET .../message` 为准——事件只当信号，不当内容。

依据是真机实测：等待期原本是黑箱，页面与图标都只能干等；而 opencode 的事件口连上先回
`server.connected`，之后逐条事件、每 15s 一拍注释，每个事件都带 `data.sessionID`，足以只认
自己 spawn 出来的那个子会话。

## Considered Options

- **轮询 `/message` 看正文有没有长**：只能看见「写完了没」，看不见「还在想」与「已写多少」，
  而且每次都是一个来回；事件流是推过来的。
- **把 `wait` 切成短片 + 自造状态端点**：`POST .../wait` 是阻塞的，切片只能靠超时打断，
  打断之后还得另找依据判断到底跑没跑完——多一层猜。
- **拿读超时当「这一阵安静」**（被真机证伪）：`http.client` 的缓冲读只要抛过一次读超时就永久
  废掉（`cannot read from timed out object`），于是第一圈安静之后的第二圈 `drain` 当场判死，
  问句秒回 `opencode-not-running`，`/status` 只闪过一帧 `queued`。现在握手才设超时，连上之后
  读是无限等的，读挪进后台线程，`drain` 只在条件变量上等时间——等的是时间，不是 socket。

## Consequences

- `dsb/events.py` 是等待期唯一的信号源：等待循环每圈先倒事件、再看 `/message`，断流或停摆
  当场收场，不再陪 opencode 等满预算。
- `GET /status` 只报「现在有没有问句在途、走到哪一步」，不提供任何指挥能力——指挥仍只来自
  网页那边的围栏，`/ask` 是唯一写入口。
- 扩展每 3s 轮询一次现场，每次自带 5s 超时；问不到当场翻红，所以不再另立一条「静默判死」的规矩。
- 挂不上事件流不算错：等待退化成老的阻塞 `wait`，代价只是失去现场与「断流当场判死」两样，
  不至于因为监控挂不上就把整条问答链掐了。
