# `/ask` 拆成短轮询：长 fetch 会被浏览器连答复一起收走

扩展原来对 `/ask` 挂一条长 fetch 等到底。MV3 的 service worker 对一条在途 fetch 只保它约 5 分钟：
更长的问句一过线，浏览器就把后台线程收走、连接断掉，中继算完了也写不回来（真机日志里两次
`BrokenPipeError`）。答复一丢，页面收不到回灌，按协议就当没问过——整条链静默停在原地，直到有人
手拨（真机空等过 33 分钟）。同一批真机数据还暴露了第二处：中继只要看到一段 assistant 正文就判
成功，而 opencode 一轮里正文分几段，前几段是过场话——于是中途一句被当成答完，剩下的活没人看。

决定：`/ask` 认一个可选的**轮询 id**。带上它，中继把这一趟跑在后台线程里、最多让请求挂 15s，
没出结果就回 `{"status": "pending", "id"}`；扩展带同一个 id 接着问，结果一直留在中继手里。
不带 id 仍是一趟问到底——curl 与测试那条老路不变。

## Consequences

- **每趟 fetch 都短**（≤ 15s）：service worker 一直有事做，不会被收；即便掉线重连，结果还在中继
  手里。扩展侧的兜底超时仍在，但角色从「一条长 fetch 的上限」变成「整条轮询的总时限」。
- **同一 id 只起一份活**：重复轮询只等不说；结果留最后 32 个 id，防「取到一半掉线」。
- **判「答完」跟着收紧**：只认最后一条 assistant 消息的 `time.completed`（实测形状：流式途中
  `time` 只有 `created`，这一轮跑完才补 `streamed` / `completed`）。中途那句不再算数。
- **超 5 分钟留一行 `ask-slow`**：断链时人只看得到这一行。
- 这也是 ADR-0007 那条动作流的前提之一：`/ask` 这条老通道先得不在半路把答复弄丢，
  「agent 指挥页面」的回路才有稳的下游可等。
